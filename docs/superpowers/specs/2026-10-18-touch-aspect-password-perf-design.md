# 触控、屏幕比例、客体密码与性能

用户目标：修复原生到 1920×1200 的触控偏移，默认提供适配屏幕的分辨率；1920×1200 稳定 120 fps，原生 60 fps；在 App 中设置 droid 密码。只改应用及其私有 runtime、客体文件，宿主系统保持不变，挂载仅在私有 namespace 中执行。

触控已通过真实五点注入复现：1920×1200 下目标 (1824,1140) 收到 (684,360)。View 在 service 更新启动尺寸之前创建，保留 1280×720，而 virtio ABS 为 3408×2272。另一个设备测试确认 MotionEvent.transform 不会将 rawY 从屏幕空间转换到 View 空间。更新 boot input/holder 尺寸，并用 View 局部坐标重建所有触点及历史样本，使 AVF 的 raw/local 两种读取路径一致。切换和退出仍释放触点。

EDID 保留原生 60 Hz 和固定 1920×1200 120 Hz，增加随原生比例计算的 1920 宽 120 Hz mode；该平板为 1920×1280。默认仅选择客体实际公布的匹配比例模式，旧客体无匹配模式时使用原生。UI 标识原生和适配屏幕。原生比例不匹配的手选模式保持等比显示。

密码界面要求两次一致输入。固定 droid 用户，UTF-8 1–128 字节，禁止 NUL/换行。应用内回调交给 service 执行，无 Intent、持久化或密码日志；vsock 使用有界 Base64 行协议，客体仅接受 host CID，固定 chpasswd 经 stdin 更新。成功以子进程退出和明确响应确认。旧 agent 返回通用失败。测试用凭据不保留，用户自行在 App 设置实际密码。

验证：设备 raw 坐标测试、真实五点映射与原生/1920 往返；实际 EDID 编码和 Kotlin 模式选择；密码输入/协议/状态及真实改密；APK/native pin；连续真实运动与自身 SurfaceFlinger 层时间戳，至少 60 秒并报告 p50/p95/p99，不把 120 Hz mode 当成 120 fps。性能先做同场景基线和分层测量，再按证据逐项实验；保留生产者/消费者同步和有限在途缓冲。临时探针最终移除，保留原 VM 数据。

后续 Wayland 实验：完整 KDE 会话已显示出收益，但先补齐 App 使用的同一显示控制协议，再决定是否切换默认桌面。X11 继续使用现有 XRandR；Wayland 使用当前会话的 KScreen JSON 和真实 mode ID，不伪造刷新率。会话描述仅由 droid 在私有运行目录发布，绑定 KWin PID 和启动时间，读取时校验文件、进程和 socket 所有者；过期或损坏时明确失败。模式更改后核对实际尺寸和刷新率，失败恢复旧模式。保留像素/刷新率预算与固定用户执行边界。先以临时 guest 文件验证切换、触控、光标、Esc 和完整会话；实验通过前不修改默认启动方式。性能比较继续使用同一可见运动场景、完整采样窗口和大核策略。

应用上屏实验：SurfaceControl 图层属性会持续生效，因此只在首帧设置颜色变换、圆角、层级与可见性；客体尺寸变化时更新几何与裁剪。每帧仍提交原始 AHB 和真实释放回调，不增加帧排队或延后提交。只有 apply 成功后才记录已提交尺寸。每次重新挂接都创建新图层并完整初始化。通过交替安装旧版与候选版、每次重新启动 VM 的两轮原生对照，再决定保留；1920 模式单独核对，不能将原生长帧改善说成 120 fps 达标。

客体同步优化：配对 Venus 在导出真实 semaphore sync-fd 后又等待它完成；Zink 本身会将该依赖写入 DMA-BUF reservation，后续消费者再导入并等待。只允许桌面启动器明确指定的 Xorg/KWin 进程提前返回真实 fd，保留消费者等待、宿主队列完成检查和 Surface 释放 fence。启动器通过 exec 保留 PID；Venus 同时校验 Zink engine 和当前 PID，普通应用、继承环境变量的子进程继续使用原行为。先用延迟 GPU 写入和独立 Vulkan 实例验证 DMA-BUF 同步链，再在临时客体 namespace 中交替测试完整桌面。去掉计时日志后复测，确认收益才更新客体库及启动器。宿主系统与大核策略保持不变。

应用缓冲引用复用实验：RootDisplayService 每帧关闭接收到的 AHB 包装对象，会触发 SurfaceComposerClient 按 GraphicBuffer 生命周期清理合成缓存。RootOwnedSurface 按系统唯一的 buffer ID 保留最多四个引用，重复 ID 提交同一引用；只复制句柄引用，不复制像素或新建图像。尺寸变化时清空旧引用，关闭会话时全部释放，即使停止生产者失败也完成清理。每帧仍使用原释放回调，不改变真实 GPU 依赖或上屏时机。先验证引用独立关闭、ID 隔离、有界淘汰和失败清理，再用 Perfetto 确认重复导入消失，并以完整 VM 重启后的两轮交替测试判断实际收益。继续保留现有颜色修正与 CLIENT 合成，不变更宿主或 CPU 策略。

该实验的保留范围：两轮原生吞吐提升约 14.5%，1920×1200 却低约 2.4%，所以只对超过 4,194,304 像素的高分辨率档启用引用复用，与现有最多 60 Hz 的像素预算一致。1920 档继续直接提交传入的引用；从高分辨率切换回来时先释放所有保留引用。后续若调整帧调度，需要重新配对测试后才能扩大范围，不能仅凭导入次数下降就默认 120 Hz 档也受益。

原生上屏节奏实验：使用公开的 SurfaceControl 目标呈现时间接口，将高分辨率帧排到 Android 单调时钟上的 60 Hz 时间点。仅同步帧提交线程最多等待一个周期，使目标时间最多领先一个周期，避免无限排队；迟到时跳过已错过的时间点，切换尺寸或退出高分辨率档时重置。只有 apply 成功后推进时间点。所有真实 GPU 依赖和释放回调保留，不修改物理屏幕刷新率、宿主策略或客体库。先验证时间点、迟到、失败和模式切换的状态机，再实测平均帧率、p95/p99、触控与退出；未达标的原型不保留。

时点对齐：初版自行起算的 60 Hz 时点仍出现缓冲按时到达却晚一刷显示的情况，因此原型改用 Choreographer 的实际预期呈现时间和相邻时点间隔，选取接近 60 Hz 的整数刷新周期，并预留 1 ms 的排期余量。仅在高分辨率档请求时钟回调，低分辨率和关闭时移除；跨线程只保存回调内复制的数值，时钟不可用时回退到固定周期。两次对齐新增测试先失败、后通过，最终是否保留仍由设备帧间隔决定。

1920 档重新配对验证：原路径每 12 秒约有 245 帧在显示前被后续提交替换。将同一排期器按像素预算扩展为高分辨率 60 Hz、低分辨率 120 Hz，最多提前一个目标周期提交，并在两档都保留最多四个 AHB 引用。每次尺寸或目标周期变化都重新排期；引用仍按尺寸清理，时钟在帧提交后启动、会话关闭时停止。两轮完整 VM 重启的对照中，1920×1200 从合并 93.37 提高到 103.36 fps（约 10.7%），因此扩大引用复用范围；原先仅高分辨率启用的限制由这次实测替代。中位缓冲就绪到显示延迟由约 12.2 增至 17.3 ms，尾部略低，需明确记录取舍。提前两个周期没有进一步收益，撤回该原型。该改动不代表稳定 120 fps 达标，原生节奏及输入仍需回归。

小上传缓冲复用：实际渲染线程采样将重复分配定位到 Android BLOB；KWin 的有界诊断进一步确认，普通上传分配原本没有调用者扩展，但 Zink 追加自己的 BDA 属性后，用变成非空的 pNext 禁用了缓存。在追加内部属性前记录现有 Venus/Mali 小上传路径是否允许复用；只有已明确启用该路径、可供 CPU 访问但不保证缓存一致、无外部/专用分配扩展且未要求禁止子分配的缓冲，才恢复进入现有缓存。缓存的容量、淘汰、引用和 GPU 完成检查保持原状，独立小分配与 DMA-BUF 缓存同步也保留。用真实分配函数前半段编译回归，验证内部 BDA/优先级属性不会误禁复用、外部链和其他驱动/配置仍走旧行为；再通过同源码交替运行、实际画面与原生档回归判断收益。该项只改客体私有图形库。
